# The agent refuses to start without include rules

When `includePackages` parses to no prefixes, the agent logs one ERROR and disables itself for the life of the JVM: nothing is instrumented, no endpoint module is installed, and nothing is exported. The collector sees no instance at all. This is what a failed bootstrap-holder install already does, for the reason given there: a missing instance is a visible signal at the collector, and a misleading one is not.

With no include rules, the agent used to log a WARNING and instrument every class outside the JDK, third-party libraries included. That puts probes on the hottest code in the process (serialisers, servlet dispatch, event loops) and multiplies transform time, probe memory and manifest size, since a Spring Boot application loads tens of thousands of library classes against a few hundred of its own. All of that cost is spent in the adopter's production JVM, and every finding it buys is about code the adopter cannot delete. A library method this service never calls is still used by other consumers of that library, so even within its own scope the claim is wrong. The one question library code could answer, whether a jar is used at all, ADR 0030 already answers from class loads and references, without a single library probe.

Every adopter has a value to give. Whoever adds `-javaagent` to a service knows its package root, and the realistic setting is one or a few company prefixes (`com.acme`), which also take in the internal shared libraries that arrive as jars, the other code an adopter can delete.

"No include rules" means anything that parses to an empty prefix list: an absent option, `includePackages=`, `includePackages=;`, whitespace. An empty value is usually a templating slip (`includePackages=${APP_PACKAGES}` with the variable unset). A configuration that sets only `excludePackages` is refused the same way, since it names no scope either. `enabled=false` is checked first and stays one INFO line: an agent switched off on purpose has nothing to fix.

The ERROR names the option, says the agent is disabled, and suggests a value when one can be found deterministically. The suggestion is the main class's own package, stated as a fact about the main class rather than as a claim about the company root: "the main class is `com.acme.shop.ShopApplication`; `includePackages=com.acme.shop` covers its package, or name a broader prefix that also covers your shared libraries". The company root cannot be derived, since reverse-domain names have no fixed depth: the first two segments are right for `com.acme.shop`, wrong for `uk.co.acme.shop` and wrong for `io.github.lukedevops.demo`, where `io.github` would instrument every library published from GitHub. The main class's package is the root Spring Boot's own component scan assumes.

The main class comes from the `sun.java.command` system property. When its first token names a jar, the jar's manifest is read: `Start-Class` when present, since Spring Boot's launcher is the `Main-Class` of every Boot fat jar and war, otherwise `Main-Class`. A module launch (`module/class`) gives the part after the slash. No suggestion is made when the main class cannot be found, has no package, or sits in a launcher or framework package that says nothing about the adopter's code: `org.springframework.boot.loader` (every Boot launcher, 2.7 through 4.1), `io.ktor.server` (Ktor's `EngineMain`, one per engine, in 2.x and 3.x) and `org.apache.catalina` (Tomcat's `Bootstrap`). Those names were read out of spring-boot-loader 2.7.18 and 3.1.12, spring-boot-loader-tools 4.1.1, ktor-server-netty, -cio, -jetty and -tomcat 2.x and 3.x, and tomcat-catalina 10.1.34. A wrong suggestion is worse than none: pasted in, it produces an instance with zero probes, whose empty never-hit list reads as a service with no dead code.

## Considered options

- **Keeping the old behaviour and filtering at the collector.** Rejected: the cost lands in the adopter's JVM before the collector sees a byte, and a filter there cannot take it back. JaCoCo's agent does default to `includes=*` and filter at report time, but it runs in test JVMs, where overhead does not matter; this agent runs in production.
- **Running a degraded mode.** Keep the endpoint tier and ADR 0030's unloaded status, which do not need the include rules, and place no method or branch probes. Rejected: the collector would receive an instance with zero probes and report nothing never hit, which reads as "no dead code", the silent, confident, wrong outcome. Avoiding that would take a new wire field saying the probe tiers were off, and the fix it spares the adopter is one option.
- **Inferring the scope from where classes come from.** Directories and `BOOT-INF/classes` would be the adopter's, jars would not. Rejected: in a multi-module build the sibling modules arrive as jars under `BOOT-INF/lib`, are dropped, and read as nothing.
- **Inferring the scope from the main class's package and applying it.** Rejected: the main class is often not the adopter's (`JarLauncher`, Ktor's `EngineMain`, Tomcat's `Bootstrap`), and each such guess instruments none of the adopter's code, the degraded mode's zero-probe instance again. The same logic is kept, but only to suggest a value in the error, never to apply one.
- **An explicit way to ask for everything, such as `includePackages=*`.** Not built. Nobody has shown a need, ADR 0030 covers the one real use without library probes, and a `*` that exists gets copied into production configurations. It can be added later without breaking anything.
- **Warning on a broad prefix such as `includePackages=com`.** Rejected: the line this ADR draws is between an adopter who forgot and one who chose, and `com` was chosen. Any depth threshold fails on the table above, since `io.github` has two segments and is still enormous.

## Consequences

- An empty include list matches nothing in `TypeMatchPolicy.isIncluded`, where it used to match everything. The refusal lives in `Agent.start`, and no other path (a test harness, the testkit, a future embedding of the agent) can reach "instrument everything" by accident: with no include rules there is one meaning everywhere, and it is "nothing".
- ADR 0030's rule for an unset include list, where origin decided which jars were the adopter's, is unreachable and removed from `JarClassifier`. `ProbeManifest.references_recorded` stays on the wire and is always true from a running agent; collectors and the server keep reading it, and removing a field would break the schema for nothing.
- The testkit's startup-timeout message names `includePackages` as a likely cause beside the `-javaagent` flag and the flush interval, since a refused agent sends no heartbeat. Its KDoc example and the README's attach example set `includePackages`, and the README lists the option as required.
- An adopter who wants only the endpoint tier still sets `includePackages`. The endpoint tier ignores the include rules once the agent is running.
